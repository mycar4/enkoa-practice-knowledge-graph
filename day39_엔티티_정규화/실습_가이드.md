## 같은 입력이 두 교안으로 이어집니다

개념은 설명을 위해 만든 가상 도서관 트리플로 확인합니다.  
대출, 저자, 분야와 만남의 6관계로 같은 책과 사람이 주어 또는 목적어로 등장해도 타입과 표준 ID가 유지되는지 확인합니다.  
실제 실습은 단위 프로젝트 2의 Python 라이브러리 문서 추출 저장본에서 선정한 Seaborn 트리플입니다.

| 범위 | 원문 | 트리플 | 주어와 목적어 출현 | 골드 개체 수 |
|---|---:|---:|---:|---:|
| 교안 01과 02 | 6문서 | 22행 | 44건 | 19개 |
| 과제 LV1 | 2문서 | 8행 | 16건 | 8개 |
| 과제 LV2 | 4문서 | 14행 | 28건 | 14개 |

`sns.kdeplot`과 `kdeplot`은 원문의 import와 호출을 대조해 같은 함수로 연결합니다.  
반면 이름이 `rugplot`인 문서와 함수는 타입과 대상이 다르므로 구분합니다.

- `triple_id`: 추출된 관계 한 행의 ID입니다.
- `mention_id`: 그 행의 주어 또는 목적어 자리의 ID입니다.
- `standard_id`: 같은 그룹의 출현에 함께 부여하는 프로젝트 내부 ID입니다.

`entity:t01:object`처럼 그룹의 대표 출현 ID 앞에 `entity:`를 붙입니다. 외부 기관 발급 코드는 아닙니다.  
노드는 통합해도 원래 이름, 관계, 출처와 근거는 각각 보존합니다.

## 실행 준비

트리플 추출 API를 다시 호출하지 않고 저장 파일을 읽습니다. 교안은 상단에서 실습용 Neo4j에 연결합니다.
과제는 LV1의 선택 실습과 LV2의 9번 직전에 연결하므로, 그 앞의 필수 파이썬 문항은 DB 없이 진행할 수 있습니다.

```bash
# 실습자료 폴더의 기존 환경에 필요한 패키지를 설치합니다.
uv add jupyter neo4j python-dotenv langchain-openai pydantic requests
```

DB 실습에는 Neo4j 5.26 이상과 GDS, APOC 플러그인이 필요합니다.  
노드는 원래 `entity_type`을 라벨로 사용하며, 관계 저장은 원래 관계 타입을 지정한 `MERGE`를 사용합니다. 기존 중복 노드 통합은 APOC를 사용합니다. [MERGE 공식 문서](https://neo4j.com/docs/cypher-manual/current/clauses/merge/#dynamic-merge)
`.env.example`을 `.env`로 복사해 실습용 DB 접속 정보를 적고, 각 노트북의 DB 연결 준비 셀을 실행합니다.
현재 작업 폴더부터 상위 폴더로 올라가 가장 가까운 `.env`를 읽습니다. 프로젝트 최상위에만 있어도 학생용과 정답에서 찾을 수 있습니다.

| 실습 | 확인할 결과 |
|---|---|
| 교안 01 GDS | OpenAI 임베딩의 KNN 후보와 공통 문서 이웃의 Node Similarity 후보 |
| 교안 02 APOC | 같은 ID의 노드를 통합해도 적재한 관계와 근거 보존. 실제 건수는 연결 결과로 확인 |
| 표준 ID 적재 | 같은 입력을 두 번 적재해도 노드와 관계 수 유지 |

교안 01의 GDS 준비 셀은 검색용 라벨의 노드를 초기화합니다.  
교안 02의 적재 준비 셀은 현재 자료의 표준 ID에 해당하는 노드와 연결된 모든 관계를 초기화합니다.  
연결 셀에서 접속을 확인한 뒤, 아래 Cypher 셀을 순서대로 실행합니다.

교안 01의 3-3절은 `text-embedding-3-large`의 `dimensions=768` 설정으로 이름과 타입의 임베딩을 실제 생성합니다.  
도서관 대표 이름 3개와 Seaborn 대표 22개 모두 노드 저장, GDS 투영, KNN 검색 순서로 실습합니다.  
`.env`의 `OPENAI_API_KEY`가 필요하며, 해당 셀을 다시 실행하면 API를 다시 호출합니다.  
과제 LV1의 GDS 선택 실습도 같은 임베딩 방식을 사용합니다.
교안 01 핵심 코드도 대표 22건을 새로 임베딩하고, 같은 GDS 설정으로 세 방법의 후보를 합칩니다.

교안 01은 `ChatPromptTemplate`과 `ChatOpenAI(model="gpt-5.6-luna")`로 동일 개체 여부를 판정합니다.  
`.env`에 `OPENAI_API_KEY`를 적고 판정 셀을 실행하면 바로 API를 호출합니다.  
교안 01은 많은 후보의 응답 누락을 줄이도록 10쌍씩 나누며, `batch`로 최대 두 요청을 동시에 처리합니다.  
교안 02는 도서관과 Seaborn 모두 `assign_group_ids`로 그룹별 ID를 부여합니다. 추가 API 호출은 없습니다.  
교안 01의 응답 누락과 형식은 코드로 검사하고, 의미는 원문과 판정 이유를 대조합니다.

## 과제 LV1 체크리스트(교안 01·02 기초 복습)

1~11번은 API나 DB 연결 없이 진행합니다. 7번은 서술형이며 정답의 후보별 모범 서술과 비교합니다.
코딩 문항은 바로 아래 자가채점으로 확인하고, 판단 이유를 쓰는 부분은 정답의 모범 서술과 대조합니다. 앞 문항의 결과를 이어 사용하므로 순서대로 진행합니다.

- [ ] 1. 추출 결과의 출처를 보존합니다
- [ ] 2. 트리플의 양 끝을 출현 기록으로 만듭니다
- [ ] 3. 원래 이름과 비교용 이름을 구분합니다
- [ ] 4. 같은 이름에서도 타입을 확인합니다
- [ ] 5. 반복 비교를 줄일 대표 표기를 고릅니다
- [ ] 6. 문자열 유사도로 검토 후보를 찾습니다
- [ ] 7. 원문 문맥으로 동일 개체 여부를 판정합니다(서술형)
- [ ] 8. 같은 개체로 판정된 출현을 그룹으로 묶습니다
- [ ] 9. 그룹별 표준 ID를 부여하고 상태를 확인합니다
- [ ] 10. 출현별 연결 기록을 파일로 저장합니다
- [ ] 11. GDS 후보 검색의 입력과 점수를 구별합니다
- [ ] 12. 서로 다른 GDS 후보를 합칩니다(선택 실습)

6번은 교안의 0.6과 다른 0.65 기준으로 후보를 찾습니다. 높은 점수만으로 ID를 확정하지 않습니다.
3번은 앞뒤 공백만 제거하면서 대소문자·접두어·괄호·내부 공백은 보존하는지 별도 입력으로 검사합니다.
8번의 그룹을 9번의 ID 부여에 그대로 사용합니다. 같은 그룹은 같은 ID를 공유하고, 보류 출현은 ID 없이 남습니다.
11번은 문서 집합의 Jaccard 계산과 두 검색 방식의 차이를 확인하는 필수 문항입니다.
12번을 시작할 때 Neo4j에 연결합니다. GDS와 임베딩 API가 필요하며 과제 전용 레이블을 초기화합니다. 실행하지 않은 선택 실습을 통과로 처리하지 않습니다.
저장 결과는 `output/lv1_entity_links.jsonl`이며 교안의 연결 파일을 덮어쓰지 않습니다.

## 과제 LV2 체크리스트(교안 02)

LV1과 다른 14개 트리플을 별도로 읽으므로 LV1 결과 파일 없이 시작할 수 있습니다.
1~8번은 파이썬으로, 9~10번은 실습용 Neo4j와 APOC로 확인합니다. DB 연결은 9번 직전에 준비합니다.

- [ ] 1. 연결 입력의 출현 ID와 원본 필드를 검사합니다
- [ ] 2. 판정된 쌍에 대칭성과 이행성을 적용합니다
- [ ] 3. 그룹 내부의 충돌이 있으면 ID 부여를 보류합니다
- [ ] 4. 확정된 그룹마다 하나의 표준 ID를 부여합니다
- [ ] 5. ID 부여 후에도 그룹과 원본이 같은지 확인합니다
- [ ] 6. 양 끝에 표준 ID가 있는 트리플을 적재 대상으로 만듭니다
- [ ] 7. 적재 노드와 관계에 원래 기록을 남깁니다
- [ ] 8. 정밀도와 재현율, F1과 오병합을 함께 평가합니다
- [ ] 9. 표준 노드와 원래 관계를 재실행해도 중복 없이 적재합니다
- [ ] 10. APOC로 기존 노드를 통합하고 관계 이동을 확인합니다

3번은 가상의 충돌 판정으로 그룹 보류를 확인합니다. 실제 저장된 검토 기록은 바꾸지 않습니다.
8번은 ID 문자열이 아니라 같은 출현들의 묶임을 평가합니다. 보류한 출현도 단독 그룹으로 평가 범위에 남깁니다. 별도 오류 입력으로 과병합과 미통합도 확인합니다.
9~10번 모두 원래 타입인 `Document`, `ApiElement`, `Change`, `Issue`를 라벨로 사용합니다. 각 준비 셀에서 현재 자료의 표준 ID에 해당하는 노드와 그 노드에 연결된 모든 관계를 초기화합니다.
10번은 출현 노드 28개를 표준 노드 14개로 합친 뒤 원래 관계 14개의 방향, 타입과 속성을 확인합니다.

- 한쪽 ID가 미확정인 트리플은 삭제하지 않고 보류합니다.
- 고정된 전체 출현 골드로 과병합과 미통합을 평가합니다.

골드의 동일 개체 쌍은 61쌍입니다. 실제 점수는 교안 01의 판정과 DB 통합 결과에 따라 계산합니다.
생성한 ID 문자열이 골드 ID와 달라도, 같은 출현들이 같은 노드로 묶였으면 올바른 통합입니다.
정밀도, 재현율, F1을 함께 보고, 전체 오병합 쌍 수(FP)와 함정쌍의 오병합 수를 별도로 확인합니다.
오병합을 경계하므로 정밀도와 오병합 수를 우선 확인합니다.
일부 함정쌍의 오류가 0이어도 전체 자료의 오병합이 없다는 뜻은 아닙니다.


## 부록: 외부 KB로 개체 연결하기

- `canonical_name`과 `aliases`로 Wikidata 후보를 검색합니다.
- 후보마다 타입(`P31`)과 공식 웹사이트(`P856`)를 읽어 표로 비교합니다.
- 설명과 공식 사이트를 대조해 LangChain 프레임워크의 `Q117340550`을 확인합니다.
- 내부 `standard_id`는 보존하고 `external_id`, `source_kb`, `link_status`를 Neo4j에 기록합니다.
- 외부 KB에 항목이 없는 `api:seaborn.rugplot`은 연결하지 않고 사유와 함께 보류로 남깁니다.
