## 0. 왜 이 문서가 나왔나 — 검수 결과 요약

v4.0 완료 보고("ALL PASS")를 직접 코드로 검수한 결과:
- BO 8개 메뉴, CO 10개 메뉴 **전부 Supabase/API 호출 0건** - 모든 버튼이 `alert()`
  팝업과 로컬 `useState`로만 동작하고 새로고침하면 사라진다.
- 반면 `franchise/api/`에 FastAPI 백엔드가 **이미 부분적으로 실제 구현되어 있다**
  (`routers/bo.py`: 가맹학원 생성/정산조회/수기조정 3개, `routers/co.py`: 권한수정/지점생성
  2개, `routers/policies.py`, `routers/fo.py`) - 그런데 **프론트가 이 백엔드를 단 한 번도
  호출하지 않는다.** 백엔드 따로, 프론트 따로 만들어진 뒤 연결이 누락된 상태다.
- 이 백엔드는 배포 설정 파일이 없어 **어디에도 배포돼 있지 않다.**
- FO의 유일한 실제 API 호출(정책 문서 조회)은 자체 백엔드를 거치지 않고 **Supabase REST를
  프론트에서 직접 호출**하는 방식이라 `anon key`가 소스에 그대로 노출된다 - 이 패턴을
  전면 금지한다(1.3절).

**앞으로 "완료" 보고 시 반드시 첨부할 것**: 해당 메뉴의 버튼을 눌렀을 때 실제 네트워크
탭에 찍히는 API 호출 캡처(또는 curl 재현) + Supabase 테이블에 데이터가 실제로 반영된
스크린샷. UI에 메뉴/버튼이 있다는 것과 별개로 검증한다.

## 1. 27개 메뉴 CRUD 실연동 (필수, 최우선)

### 1.1 원칙
- BO/CO/FO의 모든 "생성/수정/삭제/저장" 버튼은 로컬 상태 변경으로 끝내지 말고, 반드시
  `franchise/api`의 엔드포인트를 호출해 Supabase에 실제로 반영한다.
- 화면 로드 시 하드코딩된 샘플 배열이 아니라, 가능한 한 실제 API에서 목록을 조회해
  채운다(단, 초기 데이터가 비어 있어 시연이 안 되는 경우 시드 데이터를 Supabase에
  넣어두는 방식으로 해결하고, 프론트 코드에 하드코딩하지 않는다).

### 1.2 이미 있는 백엔드부터 프론트에 연결
- BO: `POST /tenants`(신규 온보딩), `GET /tenants/{id}/billing`(정산조회),
  `POST /tenants/{id}/billing/manual-adjustment`(수기조정) - 이미 구현된 3개부터 연결.
  나머지 5개 메뉴(정책문서/권한템플릿/플랫폼통계/공지사항/계정관리)는 해당 라우터 신규 작성.
- CO: `PUT /tenants/{id}/permissions/{user_id}`, `POST /co/branches` - 연결. 나머지
  8개 메뉴(원생/출결/실기평가/앨범/수강료/학부모연동/정책조회/학원정보)는 라우터 신규 작성.
- FO: 정책 조회를 자체 백엔드 경유로 변경(1.3절), 나머지 8개 메뉴 라우터 신규 작성.

### 1.3 보안
- 프론트에서 Supabase REST/anon key 직접 호출 **전면 금지**. 모든 프론트→DB 경로는
  `franchise/api`를 거친다. 기존 FO 코드에 이미 들어간 `supabaseUrl`/`anonKey` 하드코딩도
  제거하고 자체 API 호출로 교체.

### 1.4 백엔드 실제 배포
- `franchise/api`를 실제 URL로 배포한다(AWS Lambda/ECS든 다른 방식이든 무관, **실제 접속
  가능한 URL이 나와야 함**). 배포 후 `/health` 엔드포인트 curl 결과를 보고서에 첨부.
- 프론트(BO/CO/FO 3개 Vercel 프로젝트)의 API base URL을 환경변수로 이 배포 URL을 가리키게 설정.

## 2. 신규 기능 — "성적 기록함" / "서류함" (계정 기반 이력 관리)

### 2.1 배경 (사용자 요구사항 원문 취지)
기존 공개 서비스의 `fo/grades.html`("성적추천")과 `fo/review.html`("서류첨삭")은 파일을
업로드하면 그 순간만 처리하고 브라우저 세션에만 임시 저장된다(로그인 없음, 서버 저장 없음).
사용자는 이걸 계정에 귀속된 **이력**으로 관리하고 싶어한다 - 특히 1·2학년은 성적이 학기마다
바뀌므로, 새로 업로드할 때마다 지우는 게 아니라 "몇 학년 몇 학기 성적"처럼 버전을 쌓아두고,
다음에 "성적추천"을 쓸 때 새로 업로드하지 않고 **기존에 등록해둔 것 중에서 골라서** 쓸 수
있어야 한다. 서류첨삭도 동일한 패턴(첨삭받은 문서들을 계정에 쌓아두고 재사용/조회).

### 2.2 신규 FO 메뉴 2개 (v4.0의 9개 메뉴에 추가)

| 메뉴 | 화면/기능 | 관련 테이블(신규) |
|---|---|---|
| 성적 기록함 | 업로드 이력 목록(라벨: "2026-1학기" 등 사용자가 붙임, 업로드일시), 상세보기(당시 파싱된 표), 신규 추가, 삭제, "현재 대표 성적"으로 지정 | `STUDENT_GRADE_RECORDS` |
| 서류함 | 첨삭 업로드 이력 목록(문서종류/라벨/업로드일시), 상세(당시 첨삭 결과), 신규 추가, 삭제 | `STUDENT_DOCUMENTS` |

**신규 테이블 스키마 (제안, 확인 후 확정)**:
```sql
STUDENT_GRADE_RECORDS (
  id, student_id, label,            -- 예: "고2-2학기"
  source_type,                      -- 'nice_html' | 'txt' | 'manual'
  raw_file_ref,                     -- Storage 경로(원본 파일)
  parsed_json,                      -- grades.html이 파싱한 결과 그대로 저장
  is_primary boolean,                -- "현재 대표 성적" 여부(1건만 true)
  created_at
)
STUDENT_DOCUMENTS (
  id, student_id, label, doc_type,  -- 예: '자기소개서', '포트폴리오설명'
  raw_file_ref, feedback_json,      -- 서류첨삭 결과
  created_at
)
```

### 2.3 API 계약 (기존 공개 사이트에서 호출할 것 — 필수 준수)
아래 2개 엔드포인트는 **로그인하지 않은 방문자도 호출 실패 없이 동작**해야 한다(기존
사이트는 비회원도 쓰는 무료 서비스이므로, 로그인 안 된 경우 이 API들은 "로그인 필요"를
뜻하는 명확한 상태코드/응답을 반환하고, 프론트(Claude가 작업)가 그걸 보고 "로그인하면
기록이 저장됩니다" 안내만 띄운다):

- `GET /api/v1/fo/grade-records` (인증 필요) → 로그인한 학생의 성적 기록 목록
- `POST /api/v1/fo/grade-records` (인증 필요) → 신규 저장(label, parsed_json 등)
- `GET /api/v1/fo/documents`, `POST /api/v1/fo/documents` → 서류함 동일 패턴
- CORS에 기존 공개 사이트 도메인(`www.artready.kr`)을 반드시 추가할 것 - 지금 CORS
  설정은 B2B 서브도메인만 허용하고 있어 기존 사이트에서 호출 시 막힌다(config.py 확인 요망).

### 2.4 담당 분리 (v4 검수 시 합의된 경계, 재확인)
- **Antigravity 담당**: 위 2.2의 신규 테이블/API, FO의 "성적 기록함"/"서류함" 화면 자체.
- **Claude(우리 쪽) 담당**: 기존 `fo/grades.html`/`fo/review.html`에 로그인 상태 감지 +
  "내 기록함에서 선택" 버튼 + 업로드 성공 후 "이 성적을 내 기록함에 저장" 체크박스를
  추가하는 작업. **Antigravity는 이 두 파일을 손대지 않는다**(기존 절대 금지 원칙 유지,
  이번엔 예외 없이 유지하기로 확정함).
- 따라서 2.3절 API는 Claude 쪽 코드가 그대로 호출할 수 있게 **엔드포인트 경로/요청·응답
  형식을 이 문서 기준으로 고정**하고, 변경 시 반드시 먼저 공유할 것.

## 3. 학원별 소개 페이지 + 전용 로그인 (신규)

### 3.1 배경
프랜차이즈 구조상 각 가맹학원은 자기 브랜드를 알릴 공개 페이지가 필요하다 - 학생/학부모가
로그인하기 전에 "이 학원이 어떤 곳인지"를 보고, 거기서 바로 그 학원 전용 로그인/가입으로
들어가야 한다. 지금 v4.0의 FO는 로그인 이후 화면만 정의돼 있고, **로그인 이전 단계(학원
소개, 학원별 진입 경로)가 빠져있다.**

### 3.2 신규 화면 2개

| 화면 | 경로(예) | 내용 | 담당 |
|---|---|---|---|
| 학원 소개 페이지 | `app.artready.kr/t/{tenant-slug}` | 학원명/로고/소개글/강사진 요약/합격 실적/위치/연락처 - 비로그인 공개, "로그인/가입" 버튼이 이 학원으로 스코프된 로그인으로 연결 | Antigravity(FO) |
| 학원 전용 로그인 | `app.artready.kr/t/{tenant-slug}/login` | 해당 학원 로고/색상으로 헤더만 스킨, 로그인 성공 시 그 학원 소속으로 가입/연동 | Antigravity(FO) |

### 3.3 데이터 요구사항
- `TENANTS` 테이블에 소개 콘텐츠 필드 추가 필요: `intro_text`, `logo_url`, `highlight_stats`(합격 실적 등 JSON), `contact_info`, `slug`(URL용 고유 식별자).
- 이 정보의 **입력/수정은 CO(원장)가 자기 학원 정보 화면에서** 하고(v4.0 CO "학원 기본정보"
  메뉴 확장), **게시 승인은 BO가** 한다(프랜차이즈 브랜드 일관성 관리 - v2.0 3.1절 `TENANTS.status`
  개념과 동일한 승인 흐름 재사용).

## 4. 디자인 퀄리티 추가 개선 방향

시안(첨삭펜 디자인 시스템, Claude 제작)의 톤·컬러·타이포는 그대로 따르되, 아래를 추가로 반영해
"정적으로 예쁜 화면"을 넘어 조작감 있는 완성도를 만든다:

- **마이크로 인터랙션**: 버튼 클릭/저장 성공 시 즉각적인 시각 피드백(토스트, 체크 애니메이션) -
  현재처럼 `alert()`으로 끝내지 말 것(1.1절 CRUD 실연동과도 연결).
  탭 전환, 카드 진입에 짧은(150~200ms) 트랜지션.
- **로딩/빈 상태 디자인**: 데이터 없음/불러오는 중 상태를 빈 화면이 아니라 스켈레톤 UI 또는
  안내 일러스트로 처리(예: 원생이 아직 없는 신규 학원의 CO 대시보드).
- **이모지 아이콘 교체**: 현재 시안의 이모지(📊🏫💳 등)는 자리표시자다 - 실제 구현 시
  일관된 선(line) 아이콘 세트(예: Lucide)로 교체해 톤을 통일한다.
- **학원별 브랜딩 반영**: 3절의 로고/색상 필드를 CO/FO 화면 헤더에도 부분 반영(전체 테마를
  바꾸는 건 아니고, 로고와 포인트 컬러 정도만) - 프랜차이즈 소속감을 주는 디테일.
