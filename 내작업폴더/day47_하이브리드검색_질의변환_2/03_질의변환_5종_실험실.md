# 2. 질의 변환 5종 실험실 — 사용자 질문을 검색 전에 손보는 5가지 방법

> 📌 아래 5개 기법 전부 `[우리 서비스 실 사례]`입니다 — 강의 원본 주장이
> 아니라 우리가 직접 홍익대 데이터로 실측한 결과이며, 강의 주장과 다를 땐
> (Multi-Query, Decomposition) 실측을 우선했습니다. 핸즈온 코드는
> [`01_핸즈온_실습.ipynb`](01_핸즈온_실습.ipynb) 5번 셀을 참고하세요.

질의 변환이란 **사용자가 입력한 질문을 그대로 검색에 쓰지 않고, 검색이 더 잘되도록
질문 자체를 가공하는 것**입니다. day47 교안이 소개하는 5가지 방법을 하나씩,
우리 서비스(홍익대학교 실제 질문)로 직접 실측했습니다.

**결과 요약을 먼저 보면**:

| 기법 | 채택 여부 | 실측 결과 |
|---|---|---|
| HyDE | ❌ 기각 | 9문항 평균순위 2.89 → 4.67 (악화) |
| Multi-Query | ❌ 기각 | 9문항 평균순위 2.89 → 4.00 (악화) |
| Self-Query | ❌ 기각 | 이미 배포된 하이브리드 검색 대비 추가 이득 없음 |
| Step-back | ❌ 기각 | 4문항 평균순위 5.0 → 7.0 (악화) |
| **Decomposition** | ✅ **채택** | 복합질문 4개 중 정답 포함률 0/4 → 4/4 (개선) |

**5개 중 1개만 살아남았습니다.** 왜 그런지 하나씩 봅니다.

---

## 2-1. HyDE (Hypothetical Document Embeddings)

### [개념]
질문을 그대로 임베딩하지 않고, LLM에게 **"이 질문에 대한 이상적인 답변처럼 생긴
가짜 문서"**를 먼저 쓰게 한 다음, 그 가짜 문서를 임베딩해서 검색합니다. 아이디어는
"질문 문장"과 "답변 문장"은 표현 형태가 다른 경우가 많으니, 질문 대신 답변 형태의
글로 검색하면 더 잘 맞는 문서를 찾는다는 것입니다.

### [우리 결론] 기각
"미술활동보고서는 몇 자 이내로 작성해야 하나요?" 1문항만 테스트했을 땐 좋아
보였습니다(6등→3등). 하지만 **9문항으로 확대하니 정반대**였습니다:

```
평균순위  질의그대로=2.89  HyDE=4.67   (더 나빠짐)
```

특히 "평가거부는 어떻게 하나요"는 1등 → 13등으로 폭락했습니다. LLM이 지어낸
가짜 문서가 실제 문서와 표현이 겹치기는커녕, 엉뚱한 방향으로 검색을 이끈 겁니다.

### [함정]
**1문항 테스트로 결론 내면 위험합니다.** 처음 1문항만 봤을 땐 확실히 좋아 보였는데,
표본을 늘리자 정반대가 나왔습니다. "된다!"는 느낌이 들어도 최소 여러 문항으로
검증하기 전엔 믿으면 안 됩니다.

---

## 2-2. Multi-Query

### [개념]
질문 하나를 LLM에게 **같은 뜻의 다른 표현 3개**로 바꿔 쓰게 한 다음, 원본+3개
전부로 검색해서 결과를 합칩니다("재현율을 넓힌다"는 아이디어).

### [우리 결론] 기각
```
평균순위  기존=2.89  Multi-Query=4.00   (더 나빠짐)
```
"마감시간이 언제야" 질문은 3등 → 15등으로 크게 나빠졌습니다. 재구성된 질문
표현이 오히려 검색을 헷갈리게 만드는 경우가 더 많았습니다.

### [함정]
**"HyDE보다는 안전할 것"이라는 예측이 틀렸습니다.** HyDE는 아예 새 문장을
지어내고 Multi-Query는 "같은 뜻으로 바꾸기만" 하니 더 안전해 보였지만, 실제
결과는 둘 다 똑같이 나빴습니다. "이론상 덜 위험해 보인다"는 것도 실측 전엔
근거가 안 됩니다.

---

## 2-3. Self-Query

### [개념]
질문에서 **검색어와 필터 조건을 분리**합니다. 예: "2023년 이후 페이지 10~20쪽에서
계약 조건 찾아줘" → 검색어="계약 조건" + 필터(연도≥2023, 페이지 10~20).

### [우리 결론] 기각 (다만 이유가 특이합니다)
질문에서 핵심 키워드를 뽑아 그 단어가 실제로 들어간 청크만 걸러봤더니, 단독으론
극적으로 좋아 보였습니다(평균 3.25등 → 1.00등). **하지만** 이미 배포된 RRF
하이브리드 검색(키워드 검색이 포함됨)으로 똑같은 질문을 돌려보니, **이미 전부
상위 5등 안에 들어가 있었습니다.**

```
이미 배포된 하이브리드 검색 결과:
평가자 회원가입 → 1등, 재직사실확인서 → 3등, 정정요청 → 3등, 홈페이지주소 → 1등
```

### [함정]
**약한 비교 대상과 비교하면 뭐든 좋아 보입니다.** Self-Query를 "순수 벡터검색"과만
비교했을 땐 압승이었지만, "이미 우리가 쓰고 있는 진짜 방식"과 비교하니 추가 이득이
없었습니다. 새 기법을 검증할 땐 반드시 **지금 실제로 배포된 것과** 비교해야지,
가장 약한 기준선과 비교하면 안 됩니다.

---

## 2-4. Step-back

### [개념]
구체적인 질문을 **더 넓은 배경 질문**으로 바꿔서 같이 검색합니다. 예: "이 회사가
왜 이 공시를 냈어?" → 배경질문: "이 산업 전반의 최근 동향은?"

### [우리 결론] 기각
```
평균순위  기존=5.0  Step-back=7.0   (더 나빠짐)
```

### [함정 아님 — 이번엔 사전 예측이 맞았습니다]
입시요강처럼 **사실조회형 질문 위주인 도메인**에서는 "배경지식"이 필요 없다는
사전 추론이 이번엔 실측과 일치했습니다. 다만 이것도 "항상 맞는 추론"이 아니라
"이번엔 우연히 맞은 추론"으로 취급해야 합니다 — HyDE/Multi-Query 때도 비슷한
추론을 했다가 틀렸으니까요.

---

## 2-5. Decomposition (복합질문 분해) — 유일한 채택

### [개념]
"A는 뭐고 B는 어떻게 해?"처럼 **두 가지 이상을 동시에 묻는 질문**을, 완전히
독립된 질문 여러 개로 쪼갠 뒤 **각각 따로 검색**해서 합칩니다.

### [우리 결론] 채택 — 실제로 프로덕션에 반영됨
복합질문을 통째로 임베딩하면 "두 사실의 평균적인 의미"로 뭉뚱그려져서, 둘 중
하나(대개 뒤쪽)를 거의 항상 놓칩니다.

```
복합질문 4개 중 "두 사실 모두 상위권 포함"
기존(통째로 검색)  : 0/4
분해 후 각각 검색  : 4/4   (모두 성공)
```

**실제 반영 코드** (`services/art_admission_service.py`):
```python
_QUESTION_WORDS = ["뭐", "어떻게", "언제", "몇", "누구", "왜", "어디", "무엇"]

def _looks_compound_for_rag(query):
    # 의문사가 2개 이상이면 "두 가지를 묻는 질문"으로 판단
    return sum(query.count(w) for w in _QUESTION_WORDS) >= 2
```

의문사가 2개 이상일 때만 LLM으로 분해를 시도하므로, 단순 질문에는 이 로직이
아예 작동하지 않아 비용/속도 영향이 없습니다.

### [함정] 처음 구현은 절반만 성공했습니다
맨 처음 만들었을 때는 하위질문마다 상위 3개씩만 가져오도록 짰는데, 4개 중 2개만
성공했습니다. 원인을 보니, 단독 질문으로 검색하면 정답이 상위 5개 안에 있는데
**3개로 좁히니까 빠지는** 경우가 있었습니다. 하위질문 개수를 3→5로 늘리자
4/4 전부 성공했습니다.

**교훈**: "일단 되는 것 같다"고 바로 끝내지 말고, 왜 100%가 아닌지 원인을 봐야
합니다 — 이번엔 단순히 숫자 하나(3→5) 조정으로 해결됐습니다.
