## [개념] 검색 방법은 크게 두 가지입니다

### 방법 1: 키워드 검색 (BM25) — "사서" 방식

도서관 사서에게 "정정요청"이라는 단어가 들어간 책을 찾아달라고 하면, 사서는 색인
카드를 뒤져서 **그 글자가 정확히 들어간** 문서를 찾아줍니다. 빠르고 정확하지만,
**같은 뜻이라도 다른 단어**를 쓰면 못 찾습니다 — "정정요청"을 찾아달랬는데 문서엔
"수정 신청"이라고만 쓰여 있으면 사서는 못 찾습니다.

- 장점: 특정 단어(고유명사, 숫자, 전문용어)를 정확히 찾는 데 최강
- 단점: 표현이 다르면(동의어) 놓침

### 방법 2: 벡터 검색 (임베딩) — "독심술사" 방식

독심술사에게 "정정요청 방법이 뭐야?"라고 물으면, 글자가 똑같은지는 안 보고 **의미가
비슷한** 문서를 찾아줍니다. "수정 신청 절차"라고 적힌 문서도 뜻이 비슷하니까 찾아줍니다.

- 장점: 표현이 달라도 의미가 통하면 찾음
- 단점: 짧고 사실적인 문장(예: "600자 이내")은 의미가 뚜렷하지 않아서 오히려 헷갈릴 수 있음

### 그래서 둘을 합칩니다 — 하이브리드 검색

사서와 독심술사한테 **각각** 물어보고, 두 사람의 답을 **하나의 순위**로 합치는 겁니다.
이 "합치는 방법"이 오늘 이야기의 핵심입니다.

## [개념] 합치는 방법 두 가지

### 방법 A: 가중합 (예전 방식)

사서와 독심술사가 각각 준 "확신 점수"(0~1로 정규화)를 비율대로 더합니다.

```
합산점수 = 0.7 × 벡터점수 + 0.3 × 키워드점수
```

### 방법 B: RRF (Reciprocal Rank Fusion, 새 방식)

점수 자체(확신도)는 무시하고, **몇 등이었는지**만 봅니다.

```
합산점수 = 1/(60 + 벡터순위) + 1/(60 + 키워드순위)
```

예: 어떤 문서가 벡터검색에서 3등, 키워드검색에서 1등이면:
```
1/(60+3) + 1/(60+1) = 0.01587 + 0.01639 = 0.03226
```

**왜 60을 더하냐**: 1등과 2등의 차이를 너무 극단적으로 벌리지 않기 위한 안전장치입니다
(1/1과 1/2는 2배 차이지만, 1/61과 1/62는 거의 차이가 없음 — 등수 하나 차이로 순위가
요동치지 않게 함). 60이라는 숫자는 RRF를 처음 제안한 논문(Cormack et al. 2009)의 표준값입니다.

## [우리 결론] 우리는 A에서 B로 바꿨습니다 (2026-09-22)

기존 코드(`services/art_admission_service.py`)는 방법 A(가중합)를 쓰고 있었습니다.
홍익대학교 실제 질문 9개로 두 방법을 직접 비교했습니다.

**실측 방법**: 각 질문마다 정답이 들어있는 진짜 청크를 원문에서 직접 찾아두고(예:
"평가거부는 어떻게 하나요"의 정답은 "평가거부" 단어가 실제로 들어있는 청크), 각
융합 방식이 그 정답을 몇 등으로 올려놓는지 쟀습니다.

| 방식 | 9문항 평균 순위 (낮을수록 좋음) |
|---|---|
| 가중합(기존) | 3.00 |
| **RRF(신규)** | **2.67** |

**중요 — "항상 좋아졌다"가 아닙니다.** 9문항 중 4개가 순위가 바뀌었는데, 2개는
좋아지고 2개는 오히려 나빠졌습니다:

| 질문 | 가중합 | RRF | 비고 |
|---|---|---|---|
| 마감시간이 언제야 | 1등 | 3등 | 나빠짐 |
| 재직사실확인서 제출 방법 | 4등 | 7등 | 나빠짐 |
| 정정요청 방법 | 8등 | 3등 | 좋아짐 |
| 홈페이지 주소가 뭐야 | 8등 | 5등 | 좋아짐 |

**평균은 좋아졌지만 개별로는 승패가 갈렸다** — 이게 진짜입니다. "RRF가 무조건 더
낫다"고 말하면 거짓말입니다.

**실제로 반영한 코드** (`hybrid_search` 함수 일부):
```python
_RRF_K = 60
vec_rank = {key: i for i, r in enumerate(vec_rows, 1)}
kw_rank = {key: i for i, r in enumerate(kw_rows, 1)}
for c in candidates:
    c["fusion_score"] = (
        1 / (_RRF_K + vec_rank.get(key, 10_000))
        + 1 / (_RRF_K + kw_rank.get(key, 10_000))
    )
```

## [함정] 우리가 실제로 빠졌던 함정 두 가지

### 함정 1: "순위가 나빠졌다 = 실제 답변도 나빠졌다"는 아닙니다

위 표에서 "마감시간"/"재직사실확인서" 질문은 순위가 나빠졌지만, 실제로 최종 답변을
만드는 LLM에게는 **상위 5개를 통째로** 넘겨줍니다. 3등이든 7등이든 **5등 안에만
있으면** 최종 답변은 똑같이 정확합니다. 실제로 확인해보니 두 경우 다 최종 5등
안에 들어있어서, 사용자가 받는 답변엔 차이가 없었습니다.

**교훈**: "중간 지표(순위)가 나빠졌다"와 "사용자가 실제로 받는 답이 나빠졌다"는
다른 질문입니다. 반드시 최종 결과까지 확인해야 합니다.

### 함정 2: 표본이 9개뿐이면 우연일 수 있습니다

9문항으로 "RRF가 낫다"고 결론 낸 건, 사실 통계적으로는 근거가 약합니다. 다른
학교, 다른 질문 유형으로 30~50개 더 테스트하기 전까진 "잠정 결론"으로만 다뤄야
합니다. 지금 프로덕션에 반영은 했지만, 이건 "지금 아는 한 최선"이지 "영원히
확정된 정답"은 아닙니다.
