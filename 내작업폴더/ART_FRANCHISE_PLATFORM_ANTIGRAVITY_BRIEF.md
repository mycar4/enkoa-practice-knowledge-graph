## 0. 이 문서를 읽기 전에 반드시 확인할 것

이 프로젝트(ART:READY)는 지금까지 **다른 AI/팀이 작성한 산출물에서 반복적으로
날조된 수치, 미구현 기능을 완료로 표시, 근거 없는 "검증됨" 주장**이 나와서
전량 재검증하고 정정한 이력이 있다(사내 문서 04/05/06(v1.2)/17/20(v1.0) 전부
이런 사유로 경고 배지 처리됨). 이 지시서를 받는 쪽도 **같은 문제를 반복하면
산출물 전체가 재검증 대상이 되어 오히려 더 늦어진다.** 아래 원칙을 최우선으로
지킬 것:

1. **실행하지 않은 것을 "완료"라고 쓰지 않는다.** 코드를 짰다고 "작동 확인함"이
   아니다 - 실제로 실행한 로그/캡처/curl 결과를 반드시 같이 제출한다.
2. **수치를 지어내지 않는다.** "응답속도 200ms" 같은 구체적 숫자는 실제로
   측정한 경우에만 쓰고, 측정 방법(어떤 환경, 몇 회 측정)을 같이 명시한다.
3. **없는 승인/검증 절차를 있다고 쓰지 않는다.** "QA 승인 완료", "보안 검토
   통과" 같은 문구는 실제로 그 절차를 밟았고 누가 승인했는지 증적이 있을
   때만 쓴다.
4. 불확실하면 "확인 필요"라고 정직하게 표시하고 다음 단계로 넘어간다 -
   그럴듯하게 채워 넣지 않는다.

## 1. 배경 및 이 작업의 위치

ART:READY는 현재 **Neo4j 지식그래프 기반 수험생용 무료/공개 서비스**
(대학찾기·성적추천·대학지도·입시질문·서류첨삭, `www.artready.kr`)가 이미
운영 중이다. 이번에 새로 만드는 건 이것과 **완전히 별개의 B2B 서비스 레이어**로,
미술학원이 이 서비스를 자기 학원 브랜드로 재판매(화이트라벨/프랜차이즈)할 수
있도록 **학원장·강사·학생·학부모 역할별 회원가입/로그인 + 학원 운영 관리
기능**을 제공하는 것이다.

**핵심**: 기존 지식그래프 서비스는 "회원가입 없이 누구나 쓰는 무료 공개 도구"이고,
이번 신규 서비스는 "학원이 계약해서 쓰는 유료 B2B 관리 시스템"이다. 두 서비스는
데이터베이스도, 배포 경로도, 코드베이스도 전부 분리된다.

## 2. 절대 금지사항 (반드시 준수 - 위반 시 산출물 반려)

| 금지 대상 | 이유 |
|---|---|
| 저장소의 `services/art_admission_*.py`, `api_art_admission.py`, `내작업폴더/fo/*.html`, `0X_Art_Admission_*.py`류 스크립트 **수정 금지** | 기존 운영 중인 수험생용 서비스 - 건드리면 실서비스 장애 |
| 저장소 내 숫자로 시작하는 문서(`00_`~`20_` 등 `ART_READY_` 문서 전체) **수정 금지** | 별도 문서 거버넌스 체계로 관리 중, 이번 작업물은 새 이름으로 별도 생성 |
| 기존 ART:READY용 Neo4j Aura 인스턴스 **접근/변경 금지** | 이번 작업은 RDB(PostgreSQL 등) 기반이며 그래프 DB와 무관 |
| 기존 GitHub Actions 배포 워크플로우(`deploy-art-admission-api.yml`) **수정 금지** | 신규 서비스는 별도 배포 파이프라인 사용 |
| 기존 코드/문서와 **파일명 충돌 금지** | 새 작업물은 전용 디렉토리(예: `franchise/`)에만 생성 |

**이번 단계에서 실제 코드/스키마를 구현하지 말 것.** 아래 3번(요청 산출물)의
**설계안까지만** 만들어서 제출한다 - 사용자가 검토·승인한 뒤에야 구현 단계로
넘어간다(이 프로젝트 전체가 "1단계 목록/설계 제출 → 검토 → 승인 후 진행" 방식을
일관되게 씀).

## 3. 요청 범위

### 3.1 역할(4종) 및 핵심 시나리오
- **학원장(원장)**: 학원(프랜차이즈 지점) 계정 생성, 강사/학생 초대 및 권한 관리, 학원 단위 통계 조회, 결제/구독 관리(가능하면)
- **강사**: 담당 학생 배정/조회, 학생별 진행상황 기록, 학원장이 부여한 권한 범위 내 조회
- **학생**: 회원가입 후 본인 성적/실기종목 정보 입력, 배정된 강사와의 소통, (기존 지식그래프 서비스의 성적추천/대학찾기 결과를 연동해서 볼 수 있으면 이상적 - 단, 이건 나중 단계)
- **학부모**: 자녀 계정과 연결(보호자 매칭), 자녀의 진행상황 열람(읽기 전용 수준 검토)

### 3.2 요청 산출물 (이번 단계는 이 4가지까지만)
1. **ERD(개체관계도)**: 학원/지점/역할/사용자/권한/구독(있다면) 테이블 구조. 멀티테넌시(여러 학원이 같은 시스템을 쓰되 데이터는 서로 안 보여야 함) 설계 방식을 명시할 것.
2. **인증/권한 설계**: 회원가입 플로우(역할별로 어떻게 다른지), 로그인, 역할 기반 접근 제어(RBAC) 방식. 사용할 인증 방식(예: Supabase Auth, 자체 JWT 등) 후보와 각각의 장단점 비교.
3. **API 초안 명세**: 최소한 회원가입/로그인/역할별 대시보드 조회 엔드포인트 목록과 요청/응답 형식.
4. **화면 흐름도**: 역할별로 로그인 후 처음 보는 화면과 핵심 동선(신규 코드/디자인 없이 흐름만).

### 3.3 아직 결정 안 된 것 (설계안에 "확인 필요"로 표시할 것)
- 기존 지식그래프 서비스와의 연동 범위(학생이 이 B2B 시스템에서 성적추천 결과를 바로 볼 수 있게 할지 여부) - 사용자 확인 필요
- 결제/구독 모델 여부 - 사용자 확인 필요
- 참고할 기획 초안(PPT/PDF)이 아직 공유되지 않음 - 받는 대로 반영해서 설계안 갱신

---

## 4. 진행 절차

1. Antigravity가 위 3.2의 4가지 설계안을 작성해서 제출
2. 사용자(엔코아)가 검토 - 필요시 참고 기획 초안(PPT/PDF)을 이 시점에 추가로 전달
3. 승인되면 구현 단계 착수 - 이때부터는 실제 실행 결과(스크린샷, 로그, API 응답 캡처)를 매 산출물에 첨부
4. 완료 시 엔코아 쪽(Claude)이 최종 산출물을 별도로 검증(이 프로젝트의 표준 절차) - 이 검증을 통과해야 "완료"로 확정됨
