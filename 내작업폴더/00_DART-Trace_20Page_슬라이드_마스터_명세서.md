### Slide 03. 현행 기술의 한계 (Problem Statement)
* **슬라이드 제목**: **왜 기존의 공시 요약 챗봇(Vector RAG)은 실패하는가?**
* **핵심 메시지**: "공시의 본질은 '단편 텍스트'가 아니라 '다단계(Multi-hop) 네트워크'입니다."
* **비주얼 다이어그램 (Before vs After 대비)**:
  ```text
  [❌ 기존 Vector RAG의 실패]
  "A사 CB 발행 후 어떤 자회사를 샀는가?" 
   ──> 단락 텍스트 유사도 검색 ──> CB 공시와 타법인 취득 공시가 분리되어 있어 "관련 내용 없음" (실패!)

  [✅ DART-Trace의 성공]
  (A사) ──[:FILED]──> (CB발행 공시) ──[:연쇄]──> (타법인취득 공시) ──[:TARGETS]──> (B자회사)
   ──> Neo4j 2-Hop 포인터 순회로 0.01초 만에 인과관계 완벽 규명!
  ```
* **3대 핵심 결함 체크리스트**:
  1. **다단 추론 불가**: 2개 이상의 공시를 엮어서 지분율을 계산하거나 전파 경로를 파악할 수 없음
  2. **시간 개념 부재**: 2022년 당시의 대표와 2024년 정정된 사실을 구분하지 못함
  3. **엔티티 파편화**: '삼성전자', '삼성전자(주)', 'Samsung'을 별개의 기업으로 인식
* **🎙️ 발표자 스크립트**:
  > "현재 시중의 수많은 RAG 서비스들은 문서를 조각내어 벡터 유사도로 검색합니다. 하지만 공시는 개별 단락이 중요한 것이 아니라, 'A 공시가 발생한 뒤 B 공시로 이어지는 다단계 인과관계'가 본질입니다. 단락 검색만으로는 이 2홉, 3홉 관계를 절대 풀 수 없기 때문에 기존 챗봇들은 금융 실무에서 외면받고 있습니다."

### Slide 04. 패러다임 전환 (Paradigm Shift)
* **슬라이드 제목**: **패러다임의 전환: "공시는 거대한 시계열 인과관계망이다"**
* **핵심 메시지**: "점(Node)과 선(Edge)에 시간을 입히면, 기업의 모든 자본 흐름이 드러납니다."
* **시각화 (자본시장 4대 이벤트 체인 다이어그램)**:
  ```text
  [1. 정정 공시] ──> [2. CB/BW 자금조달] ──> [3. 최대주주 지분변동] ──> [4. 계열사 타법인 출자]
    계약금액 30% 감액        100억 원 사채 발행          지분율 15% ➡️ 35% 인수        C사 신규 자회사 편입
  ```
* **핵심 정의 3요소**:
  * **Event Driven**: 모든 공시는 기업의 상태를 변화시키는 트리거(Trigger) 이벤트다.
  * **Relational**: 한 기업의 이벤트는 계열사, 대주주, 협력사로 반드시 파급된다.
  * **Temporal**: 사실(Fact)은 고정된 것이 아니라 시간에 따라 정정되고 업데이트된다.
* **🎙️ 발표자 스크립트**:
  > "DART-Trace는 공시를 정적인 문서 파일로 취급하지 않고, 자본시장의 상태를 바꾸는 '이벤트 트리거'로 정의합니다. 정정공시부터 자금조달, 지분 변동, 계열사 출자로 이어지는 인과관계 체인을 그래프 토폴로지로 구조화하는 것이 본 프로젝트의 출발점입니다."

### Slide 05. Core Rule 1: Claim-to-Fact 아키텍처
* **슬라이드 제목**: **설계 철학 1: LLM은 사실 판정관이 아니다 (Claim ➡️ Fact)**
* **핵심 메시지**: "LLM의 추출물은 '가설(Claim)'일 뿐이며, 4단계 검증을 통과해야 비로소 '팩트(Fact)'로 승격됩니다."
* **아키텍처 파이프라인 (Flowchart)**:
  ```mermaid
  flowchart LR
      D["공시 원문 문장"] --> EX["LLM 추출기"]
      EX --> CL["DisclosureClaim\n(미검증 주장 노드)"]
      CL --> VAL{"4대 헌법 검증\n(스키마·식별자·시간·원문)"}
      VAL -->|통과 ✅| FACT["Company -[:OWNS]-> Company\n(검증된 그래프 팩트 승격)"]
      VAL -->|보류 ⚠️| QUEUE["검토 대기 큐 (Review Queue)\n(Human-in-the-Loop)"]
      VAL -->|위반 ❌| DROP["오염 데이터 폐기"]
  ```
* **엔터프라이즈 차별점**:
  * LLM이 추출한 결과(`A사가 B사 지분 20% 인수`)를 곧바로 DB에 넣지 않고 `Claim` 노드로 보류
  * 원문 문장 위치(SourceChunk)와 스키마 규칙이 일치할 때만 실제 엣지로 반영
* **🎙️ 발표자 스크립트**:
  > "대부분의 생성형 AI 프로젝트가 실패하는 이유는 LLM이 뱉은 답변을 무비판적으로 DB에 넣기 때문입니다. DART-Trace는 LLM의 출력을 '주장(Claim)'으로 격리하고, 엄격한 헌법 검증을 통과한 데이터만 '그래프 팩트'로 승격시키는 Claim-to-Fact 거버넌스를 구현했습니다."

### Slide 06. Core Rule 2: 공식 식별자 우선주의
* **슬라이드 제목**: **설계 철학 2: 엔티티 식별은 LLM보다 공식 식별자가 먼저**
* **핵심 메시지**: "이름으로 엔티티를 합치지 않습니다. DART 고유 `corp_code`로 통일합니다."
* **엔티티 통합 규칙 비교표**:
  | 구분 | 대상 | 처리 규칙 (Entity Resolution Policy) | 결과 |
  |---|---|---|---|
  | **기업 (Company)** | 삼성전자, Samsung, 삼성전자(주) | DART 고유 8자리 **`corp_code: '00126380'`** 기준으로 자동 단일 노드 병합 | 노드 파편화 0% |
  | **인물 (Person)** | '김철수' (A사 대표 vs B사 이사) | 동명이인 위험으로 **자동 병합 금지** ➡️ `CandidateMatch`로 묶어 검토 큐 발송 | 오인 매칭 원천 차단 |
* **노드 속성 구조 예시**:
  ```json
  {
    "corp_code": "00126380",
    "canonical_name": "삼성전자",
    "stock_code": "005930",
    "aliases": ["삼성전자(주)", "Samsung Electronics"]
  }
  ```
* **🎙️ 발표자 스크립트**:
  > "기업명 표기가 제각각인 비정형 문서에서 AI에게만 병합을 맡기면 기업 노드가 갈라지거나 잘못 합쳐집니다. DART-Trace는 금융감독원 공식 8자리 고유번호인 corp_code를 1차 키로 삼아 기업을 완벽히 단일화하고, 동명이인 위험이 있는 인물 데이터는 엄격한 검토 큐로 분리합니다."

### Slide 07. Core Rule 3: 듀얼 타임라인 모델링
* **슬라이드 제목**: **설계 철학 3: 듀얼 타임라인 (시간의 입체적 분리)**
* **핵심 메시지**: "현실에서 유효했던 기간과 시장에 공시된 시점은 다릅니다."
* **3대 시간축 정의 및 질문 매핑**:
  ```text
  ┌────────────────────────────────────────────────────────────────────────────────────────┐
  │ [1] 현실 유효기간 (valid_from ~ valid_to)  ──> "2022년 당시 실제 대표는 누구였는가?"     │
  │ [2] 시장 공시일시 (disclosed_at)           ──> "2022년 6월 당시 시장이 알고 있던 사실은?"  │
  │ [3] 정정 관계망 (superseded_by)          ──> "나중에 정정 공시로 바뀐 최종 사실은?"     │
  └────────────────────────────────────────────────────────────────────────────────────────┘
  ```
* **엣지 속성 예시**:
  ```cypher
  (p:Person)-[:HOLDS_ROLE {
      role: '대표이사',
      valid_from: date('2022-01-01'),
      valid_to: date('2024-03-15'),
      disclosed_at: datetime('2022-01-02T09:00:00'),
      is_current: false
  }]->(c:Company)
  ```
* **🎙️ 발표자 스크립트**:
  > "공시 분석에서 가장 어려운 것은 시간입니다. 과거에 유효했던 기간, 시장에 최초로 알려진 날짜, 그리고 정정 공시로 내용이 바뀐 시점은 모두 다릅니다. DART-Trace는 이 3가지 시간축을 엣지 속성으로 완벽히 분리하여 과거 특정 시점의 지배구조 스냅샷을 100% 복원해 냅니다."

### Slide 08. Core Rule 4: 복합 신뢰도 & HITL 검토 큐
* **슬라이드 제목**: **설계 철학 4: 복합 신뢰도 평가 & Human-in-the-Loop**
* **핵심 메시지**: "AI의 자체 신뢰도 점수는 믿지 않습니다. 다중 신호(Multi-signal)로 판정합니다."
* **신뢰도 산출 공식 & 처리 정책 (Matrix)**:
  $$\text{최종 신뢰도} = \text{API 정형 매칭}(40\%) + \text{원문 인용 존재}(30\%) + \text{스키마 통과}(20\%) + \text{Critic 검증}(10\%)$$
  
  | 신뢰도 구간 | 판정 결과 | 시스템 처리 파이프라인 |
  |:---:|:---:|---|
  | **$\ge 0.90$** | **High Fact** | Neo4j 지식그래프에 **자동 즉시 적재** |
  | **$0.70 \sim 0.89$** | **Pending Claim** | **운영자 검토 대시보드(HITL)**로 전달 ➡️ 1클릭 승인 시 적재 |
  | **$< 0.70$** | **Low Risk** | 오염 데이터로 판단하여 **자동 반려 및 로그 기록** |
* **🎙️ 발표자 스크립트**:
  > "LLM이 스스로 95% 확실하다고 말하는 점수는 신뢰할 수 없습니다. DART-Trace는 DART 정형 API 데이터와의 교차 검증, 원문 텍스트 인용 유무, 스키마 검증을 종합한 다중 신호 신뢰도 모델을 구축하고, 모호한 데이터는 인간 전문가가 대시보드에서 1클릭으로 승인하는 Human-in-the-Loop를 완성했습니다."

### Slide 11. Pydantic 스키마 가드레일 & 원문 앵커링
* **슬라이드 제목**: **Pydantic 스키마 가드레일 & 원문 근거 앵커링**

  ```python
  class OwnershipClaim(BaseModel):
      owner_corp_code: str = Field(pattern=r"^\d{8}$")
      target_corp_code: str = Field(pattern=r"^\d{8}$")
      shares_pct: float = Field(ge=0.0, le=100.0)
      source_chunk_id: str = Field(description="원문 문단 ID 앵커")
  ```

### Slide 12. Neo4j LPG 물리 스토리지 & 인접 순회
* **슬라이드 제목**: **Neo4j LPG 물리 스토리지 & $O(1)$ 인덱스 프리 인접 순회**
* **핵심 메시지**: "데이터가 수억 건으로 커져도 다단계 지배구조 탐색 속도는 항상 $O(1)$입니다."
* **RDB vs Neo4j 물리 엔진 비교 다이어그램**:
  ```text
  [RDB: B-Tree 인덱스 조인 탐색]                  [Neo4j: Index-Free Adjacency 포인터 순회]
  Table A ──> Index Search ──> Table B           (노드 레코드) ──[직접 메모리 포인터 주소]──> (다음 노드 레코드)
  조인 단계마다 O(log N) 비용 발생 ➡️ 3-Hop 이상 지연     데이터 규모와 무관하게 O(1) 초고속 순회 유지!
  ```
* **물리 스토리지 스펙**:
  * **NodeStore**: 노드 ID, 레이블 비트맵, 속성 포인터
  * **RelStore**: 출발 노드 포인터, 도착 노드 포인터, 다음 관계 체인 포인터
  * **제약조건**: `CREATE CONSTRAINT FOR (c:Company) REQUIRE c.corp_code IS UNIQUE;`
* **🎙️ 발표자 스크립트**:
  > "Neo4j를 선택한 기술적 이유는 인덱스 프리 인접성(Index-Free Adjacency) 때문입니다. RDB는 지배구조를 3단계만 타고 들어가도 조인 연산으로 서버가 멈추지만, Neo4j는 노드 레코드 안에 다음 노드의 메모리 주소를 직접 쥐고 있어 5단계 순환출자망도 0.001초 만에 순회합니다."

### Slide 13. 3대 킬러 비즈니스 질의 시나리오
* **슬라이드 제목**: **실무를 관통하는 3대 킬러 Cypher 질의 시나리오**
* **핵심 메시지**: "증권사 애널리스트와 PE 실사팀이 매일 수작업으로 하던 조사를 쿼리 한 줄로 자동화합니다."
* **3대 시나리오 요약 카드**:
  1. **[시나리오 1] 자금조달 연쇄 투자 추적**
     * `(A사)-[:FILED]->(CB발행)-[:연쇄]->(타법인취득)->(B자회사)` ➡️ 6개월 내 자금 유입 경로 규명
  2. **[시나리오 2] 정정공시 감액 체인 조기 감지**
     * `(정정공시)-[:CORRECTS*1..3]->(최초공시)` ➡️ 계약금액이 30% 이상 깎인 부실 징후 포착
  3. **[시나리오 3] 대주주 임원 겸직 & 순환출자 고리**
     * `(대주주)-[:OWNS|HOLDS_ROLE*2..4]->(순환고리)` ➡️ 숨겨진 특수관계인 지배력 시각화
* **🎙️ 발표자 스크립트**:
  > "DART-Trace가 해결하는 3대 실무 킬러 쿼리입니다. CB 발행으로 조달한 자금이 어떤 계열사 지분 취득으로 흘러갔는지, 단일판매 공급계약이 정정공시를 통해 대폭 감액되었는지, 그리고 대주주가 복수 계열사를 지배하는 순환출자 고리가 존재하는지를 완벽한 Cypher 쿼리로 풀어냅니다."

### Slide 14. 하이브리드 검색 아키텍처
* **슬라이드 제목**: **하이브리드 검색: Graph(관계) + Vector(원문) + SQL(수치)**
* **핵심 메시지**: "질문의 성격에 따라 가장 완벽한 특화 엔진을 융합합니다."
* **3대 엔진 역할 분담 매트릭스**:
  | 엔진 | 주력 역할 | 질문 예시 | 반환 데이터 |
  |:---:|---|---|---|
  | **🕸️ Neo4j (GraphDB)** | **관계·경로·네트워크 토폴로지** | "A사 최대주주가 지배하는 모든 계열사는?" | 다단 서브그래프 경로 |
  | **🔍 Qdrant (VectorDB)** | **비정형 본문 시맨틱 검색** | "공시 원문에서 풋옵션 특약 조건을 찾아줘" | 원문 텍스트 단락 |
  | **📊 DuckDB/SQL** | **수치 집계 및 정형 필터링** | "최근 3개년 유상증자 발행 총액은?" | 정확한 수치 계산값 |
* **RRF (Reciprocal Rank Fusion) 융합**:
  * 각 엔진에서 나온 랭킹 결과를 RRF 알고리즘으로 결합하여 LLM 컨텍스트에 주입

  ```text
  🤖 [DART-Trace 답변]:
  ```
